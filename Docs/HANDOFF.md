# MacBook Air側Codexへの開発引き継ぎ

更新日：2026-10-03（日本時間）。対象：Our Notes Analyzer、アワーノーツ向けローカルmacOS試作版 v0.2.0（ビルド2）。

## 最新の変更：ブランドUIの最終ポリッシュ

2026-10-03、「アワーノーツ・ロゴ（ブランド）」だけの表現ルールを整理。配色値・サイドバー選択・一覧のAppKit選択描画・フォント候補・画面構成を維持した。

- `BrandLineRole` で、画面開始の3色、通常セクションの青灰／水色2本、特別成果の主役色を長くした3本を定義。成果カードの既存上辺線を小さな3本線へ置換し、通常見出しからピンクを外した。
- `BrandCategory` の8カテゴリへ英字を限定し、通常13pt・ページ15ptのキッカーへ縮小。サイドバーのOur Notesは29ptを維持。CatalogはLibrary、プレイ詳細のRecordはHistoryへ統一した。
- `BrandEmptyState` で検索結果なし・譜面未選択・未プレイ履歴・記録ゼロのホーム／分析・取込前を共通化。英字・線は装飾として読み上げ対象から除外し、各画面の日本語・アクションは維持する。
- Swift221件・Python6件成功。線の役割と選択行の文字コントラストを2件追加。実画面確認と残る制約は [検証記録](Verification.md) の冒頭を参照。

## 前段の変更：ロゴのブランドUI比較案

2026-10-03、既存3テーマを保持し、4つ目の「アワーノーツ・ロゴ（ブランド）」を追加。保存値は `ourNotesBrand`。旧 `ourNotesLogo` の色・大型の帯・セリフ体は比較用にそのまま残した。ライト／ダークの保存キー・設定方法は変更していない。

- `BrandStyle.swift` に `BrandColors`、`BrandTypography`、`BrandNoteLines`、`BrandScriptLabel`、`BrandSectionHeader`、`BrandPageHeader`、`BrandAccentMark`、`BrandSidebarNavigation` を追加。青灰・水色・くすみピンクの装飾色と、可読性を確保した文字・操作色を分けた。
- スクリプト英字はSnell Roundhandを優先し、Apple Chancery → Noteworthy Light → システムのセリフ体イタリックへフォールバック。外部フォントを追加せず、日本語・データ・操作ラベルはシステムフォント。装飾英字・斜線はアクセシビリティから除外する。
- 新テーマだけサイドバー、全ページの見出し、成果カード、ホームの達成見出し、取込・分析・設定の重要セクションへ共通モチーフを適用。大きい帯、背景グラデーション、影は新テーマで使用しない。APはピンク、FCは青、コンボ更新は青灰＋青。未知・未プレイはグレーを維持。
- `BrandLibraryTable.swift` は新テーマだけの同じ5列のAppKitテーブル。標準SwiftUIテーブルの濃い選択塗りを避け、`NSTableRowView.drawSelection` で薄い水色を描く。ネイティブのキーボード選択・スクロール・アクセシビリティと既存の選択ID／詳細連動を使う。従来テーマは元のSwiftUIテーブル。
- 最終のテスト・実画面検証は `Docs/Verification.md` 冒頭を参照。DB、保存履歴、OCR、集計・分析ロジック、テーマの既存raw値を変更していない。

## 前段の変更：ロゴを参考にした配色と表示モード

2026-10-03、従来の「アワーノーツ風」を保持したまま「アワーノーツ・ロゴ」を追加。ユーザー提供ロゴの青灰・水色・くすんだピンクと、斜めに重なる帯を参考にしている。

- `AppTheme.swift` に3つ目の配色と `AppAppearance` を追加。既存の `appearanceTheme` のraw値 `system`／`ourNotes` は維持し、新配色は `ourNotesLogo`。表示モードは別キー `appearanceMode` に `system`／`light`／`dark` を保存する。
- `AppearanceSettings.swift` に3つの配色プレビューと表示モードの選択を分離。「システムに合わせる」が初期値で、ライト／ダークを明示するとMacの外観に関係なく固定する。`Main.swift` で `NSApplication.appearance` を `aqua`／`darkAqua`／`nil` に設定し、パレットと標準コントロール・シートに反映する。SwiftUIの `preferredColorScheme(nil)` では固定表示が残ったため、システム追従への復帰もAppKitで明示する。
- `LogoDecoration.swift` のベクターの帯をサイドバーとホームに使用。ロゴ画像そのものの保存・読込、実行時の通信は追加していない。旧テーマの色と装飾は保持する。
- 保存モデル・集計・OCRには変更なし。検証用 `.home.light.verification` はシステム追従時に限ってライト環境を模擬し、明示した表示モードを優先する。実画面確認の結果は [検証記録](Verification.md) の冒頭を参照。

## 前段の変更：成果ホームと配色切替

2026-10-03、ユーザーが「最近の成果」案を選択。ホームにはスコアを表示せず、初AP・初FC・最大コンボ更新、判定詳細、これまでの達成譜面数、最近登録したプレイを表示する。スコアはこのゲームではキャラの強さに左右されるため、ホームの成果判定にも使わない。

- `HomePresentation.swift` が確定履歴から読み取り専用で集計する。今回の新規登録IDを優先し、再起動後は登録日時順の最新20件。1譜面につき初AP→初FC→最大コンボ更新を優先する。コンボは同一譜面の既知の過去最大値と比較し、未知や初回は更新にしない。
- `HomeView.swift` に成果カード・達成数・最近6プレイ・判定詳細を実装。詳細から既存の譜面履歴へ移動できる。確認待ちや失敗は取込画面へ誘導する。プレイ日時と登録日時を区別する。
- `AppTheme.swift` の共通パレットをホーム・一覧・取込・分析・マスター・設定に適用。「環境・プリセット」で配色を選び、`@AppStorage("appearanceTheme")` へ保存する。表示モードの独立選択は上記の最新変更で追加した。
- 色の参考は提供スクショと[公式サイト](https://bang-dream-on.bushimo.jp/)・[ゲーム紹介](https://bang-dream-on.bushimo.jp/system/)（2026-10-03確認）。白紫／深い紺、青紫・シアン・ピンクを使用。公式指定色とはしていない。実行時のWebアクセスや画像資産は追加しない。
- 保存モデル・DB形式・既存履歴・OCRの登録条件は変更していない。`HomeVerification.swift` はメモリ内の人工履歴だけを使用する。検証結果は [検証記録](Verification.md) を参照。

## 前段の変更：楽曲一覧「譜面で比較」

2026-10-03、ユーザーが推奨案を採用したため、楽曲一覧を1譜面1行の比較表へ変更した。曲名／難易度、Lv、達成、最高スコア、回数を表示し、曲名・別名、難易度、Lv、達成状態で絞り込める。右側を「概要／履歴」に分け、既存の編集・削除、スコア推移、FAST/SLOW、タイミング分析への導線を保持した。

- `LibraryPresentation.swift` が表示用集計・検索・並べ替えを担当する。最高スコアは全環境・全設定の記録から求め、そのプレイの環境を表示。APはFCに含め、後のプレイで過去の達成を消さない。欠測、達成不明、未プレイを区別する。
- `RootView` が検索・フィルタ・並び順・選択・詳細タブを保持する。分析画面との往復で状態を維持し、絞り込みで対象外になった選択は解除する。DBへ画面状態は保存しない。
- `ChartDetailView.swift` に詳細表示を分離し、`LibraryView.swift` の既存 `PlayEditor` を再利用した。保存モデル・スキーマ・既存履歴は変更していない。
- Swift203件（コア114・アプリ89、新規8件）が全件成功。別Bundle IDの署名アプリと人工履歴を使い、検索・複合フィルタ・編集・削除・分析との往復・最小幅を実画面で確認。詳細は [検証記録](Verification.md) の冒頭。
- UI確認用の `--show-library-verification` とBundle ID末尾 `.library.verification` は、通常DBを開かずメモリ内の人工履歴だけを使用する。

「曲ごとにまとめる」は、今後の切替表示として追加する段階。今回の依頼範囲には含めていない。分析の整理→取込確認→楽曲一覧→成果ホームの一連のUI改善を実装した。

## 前段の変更：要点を先に見せるUIと自動取込

2026-10-02の追加依頼で、確認中心の取込を「OCR→正規マスター照合→整合性チェック→自動登録」に変更した。**以下の旧記述の「全件手動登録」は廃止**。自動登録にAFMは使わない。画面はサマリー／タイミング調整／詳細データを分け、取込結果と項目別確認を追加した。

現行仕様は [自動取込](AutomaticImport.md)、検証結果は [検証記録](Verification.md) の最新節を参照。初回の一括検証後に6/9誤読を発見し、文脈付きOCRと数値の追加照合を実装した。最終の実画像検証状況はVerification.mdを参照。型への追加はOptionalで、旧DBの履歴を推測して更新しない。

2026-10-03までに、残っていた実画面テストを完了。正常結果の自動登録、1項目だけの修正、矛盾時の登録拒否と入力保持、履歴編集、重複スキップ、分析3タブ、削除と集計の更新をメモリDBで確認した。確認項目数と警告文の重複表示を修正し、自動取込回帰14件を再実行して全件成功。その後、ユーザーの依頼で上記の楽曲一覧へ着手した。

入口は `ResultCore/AutomaticRegistration.swift`（証拠・照合・整合性・confidence・重複）、`OurNotesApp/AutomaticImport.swift`（一括処理・自動保存・項目確認）、`AutomaticImportVerification.swift`（使い捨てDBによる実画像検証）。

## ユーザー要件と現在地

SwiftUI中心のネイティブアプリ。AI API・外部API・クラウドサービス・ネットワーク通信を使わず、Mac内で画像解析・保存・統計計算を完結させる。最初の対応タイトルはアワーノーツのみ。Apple Visionが画像OCRを担当し、Foundation Modelsは低信頼度・曖昧な項目で、OCR根拠から作った許可候補IDを選ぶ任意の補助レイヤー。AFMは新しい値を生成せず、採用は確認画面で項目ごとにユーザーが行う。利用できない場合もVisionと手動確認を継続する。詳細は [AFM補助仕様](AFM.md)。

試作版の主要機能は実装済み。2026-10-02の追加指示で、3サイトを照合した84曲・336譜面の正規マスター、自動収集スクリプト、起動時の自動適用を追加した。ユーザーは手動でマスターを登録しない。既存の登録マスター・手修正値はWeb由来の値へリセットし、履歴は保持する。詳細は `CatalogFormat.md`。以下の過去の検証記録よりこの仕様を優先する。

| 項目 | 現在の実装 |
|---|---|
| 一括取込 | ファイル選択・Finderからのドロップ。PNG/JPEG/HEIC、1回100枚、1画像80MB・最大辺20000pxまで |
| ローカルOCR | Apple Vision。通常リザルト／FAST・SLOW詳細／設定画像を識別。曲名、難易度・レベル、スコア、コンボ、FC/AP、5判定を読み取る |
| OCR補助 | Foundation ModelsはOCR根拠から作った許可候補IDの選択に限る。候補は一時的に保持し、確認画面で明示採用する。詳細は `AFM.md` |
| 確認・修正 | 一時画像プレビューと入力欄。曖昧な結果は確認待ち。譜面の登録先選択、通常・詳細画像の明示統合、既存プレイ候補への統合 |
| 登録確認 | 正規譜面と数値を安全に一意確定できる結果は自動登録。曖昧・矛盾のある項目だけ確認。取込開始時の環境・固定タイミングを保持 |
| 重複処理 | 画像指紋や日時を含む完全一致はスキップ。結果領域の知覚ハッシュや内容が近い記録は候補提示し、確認して統合 |
| 撮影日時 | EXIF/XMP/IPTCの撮影・作成日時を優先。未取得時だけ対応スクショ名から取得。オフセットなしは日本時間として表示し、候補の選択・手入力・不明を選べる。統合後も画像別の匿名日時根拠を保持 |
| 分析用JSON | 傾向分析画面から、全マスターと確定履歴・当時の環境／設定・日時根拠を一括出力。形式版1・分析ルール版2・アプリ版を識別し、欠測はnull |
| 保存 | ローカルSwiftData。画像本体・サムネイル・全文OCR・元画像パス・永続アクセス情報を保存しない |
| 成果ホーム | 初AP・初FC・最大コンボ更新、FC/AP達成譜面数、最近登録したプレイ。スコアは表示・成果判定に使わない。判定詳細から譜面履歴へ移動 |
| 配色 | 標準／アワーノーツ風／アワーノーツ・ロゴ／アワーノーツ・ロゴ（ブランド）と、システム追従／ライト／ダークを別々に選択。次回起動にも保持 |
| 楽曲・譜面一覧 | 1譜面1行の比較表。曲名・別名、難易度、Lv、未プレイ／未FC／未AP／FC／AP、アーカイブで絞り込み。記録日・曲名・Lvで並べ替え |
| 履歴 | 譜面ごとのプレイ履歴・スコア推移・FAST/SLOW、履歴編集。現在の曲名・レベルはWebマスターに統一 |
| 傾向分析 | 難易度／プレイ時レベル別、環境別。FAST/SLOW、各判定率、FC/AP率、平均スコアのグラフと集計表。中央値、標本SD、最小・最大、対象件数も表示 |
| 環境・設定 | M2 iPad Pro 11インチ固定。スピーカー／イヤホンは記録用で集計を分割せず、遅延推定・補正なし。環境ごとにタイミングを固定。登録時の変更有無、初回確定・変更専用UI、任意の設定画像に対応。過去スナップショットを保持 |
| タイミング候補 | 0.01刻み・−3〜3・SLOWで増加の仕様をユーザー確認済み。譜面ごと直近10件を曲横断・プレイ時レベル別に集計し、3曲・詳細500件などの条件を満たすと1ステップ候補を表示。ゲームで変更した確認を経て明示記録 |
| マスタ・プリセット更新 | 楽曲マスターはWebから自動生成して同梱し、起動時に正規データへ置換。プリセットはローカルJSON選択・確認・版管理 |

同梱正規マスターは公開情報で収録済みを確認した84曲・336譜面。予定曲は含めない。`sample-catalog.json` は旧IDの移行・テスト用だけに使用する。

## 変更時に壊してはいけない前提

### ローカル完結と画像寿命

- アプリからWebへアクセスしない。外部パッケージ依存なし。CloudKitは `.none`。権限はApp Sandboxとユーザー選択ファイルの読書き（取込とJSON保存）で、ネットワーク権限を付けない。
- Foundation Modelsには画像や保存履歴を渡さず、OCR由来の根拠と許可候補IDだけを渡す。応答は候補ID選択として検証し、登録値はユーザーが確認画面で採用した場合だけ編集欄へ反映する。
- 原画像は変更・削除しない。解析中の画像と確認用プレビューは一時的にメモリ保持し、登録・破棄・終了で解放する。確認待ちは再起動で復元しない。
- 永続化するのは解析値、内部ID、履歴・環境スナップショット、確認状態、プリセット版、日時・画像別の正規化日時根拠、SHA-256・知覚ハッシュ・レイアウト情報。再解析用画像、画像への恒久アクセス、全文OCRを追加保存しない。
- AFM用の根拠、候補、プロンプト、応答は実行中だけメモリに保持し、保存スキーマ `schemaVersion = 1` は変更しない。
- 通常保存先はサンドボックスコンテナのApplication Support内 `OurNotesAnalyzer/results.store`。インポートしたプリセットは同じディレクトリの `preset.json`。起動方法によって保存先が変わるため、正確なパスは画面または `AppModel.storePath` で確認する。

### ID・マスタ・履歴の分離

- 表示曲名を恒久IDにしない。SongとChartは内部UUID。外部データとは `(gameID, sourceID, kind, externalID)` のBindingで紐付ける。
- 曲名・レベル・並び順から外部IDを毎回生成しない。収集ツールを変更しても同じ台帳の `sourceId` と固定IDを保持する。
- 正規マスターの値を優先し、旧マスターと曲・譜面のユーザー修正をリセットする（2026-10-02ユーザー指定）。対応できる内部UUIDと既存履歴は保持する。
- 各プレイは曲名・難易度・レベル・環境設定・プリセット版の当時値を保持する。マスタ更新や現在設定の変更から過去値を上書きしない。履歴編集や今回のバッチへの設定適用は明示操作に限定。
- マスター置換時は正規曲1件に確定する旧登録だけを引き継ぎ、重複譜面の履歴を集約する。別バージョンや曖昧な旧曲はアーカイブで保持。通常のOCR照合は曖昧なら明示選択または拒否。
- Web収集で既存IDが消えたら公開を中止する。正規マスターに対応しない旧登録は履歴があるものだけアーカイブで保持し、履歴なしの旧項目は削除する。
- マスタの `revision` とプリセットの `version` は内容変更時に増加させる。同版の異なる内容や旧版を黙って受け入れない。JSONから任意コードを実行しない。

### 判定値・重複・統合

- 欠測 `nil` と読取済みの0を区別する。`total`、`fast`、`slow` は独立した任意値。
- 詳細画面ではPERFECTのFAST＋SLOWが通常画面のPERFECT総数に一致しない。総数をFAST/SLOWから補完しない。APでもPERFECTのFAST/SLOWは存在する。
- 達成状態は `unknown / none / fc / ap`。不明を未達成やゼロへ変換しない。APはFCにも含める。
- アワーノーツのFCはGOODを許し、BAD/MISSの正の判定数だけを矛盾とする。APはGREAT/GOOD/BAD/MISSの正の判定数を矛盾とする。GOODだけを根拠に未FCとはしない。アシストモードは対応対象外で、表示検出時に取込を拒否する。
- 数値OCRの同一画像・項目・領域で、最有力との差0.10以内の候補が6/9だけで競合すると「6/9判定曖昧」。再読取の根拠を保持し、自動登録を止める。AFMは項目別の新規セッションに分け、他の判定数・合計・暫定値で推測せず、OCR由来の許可IDだけを選ぶ。未決定は手動確認。詳細は `AFM.md`。
- 6/9を含む数値は単一候補でも実画素を再読取する。`photo`の往欄印通常画像で元のMISS「9」／再読取「6」の競合を確認済み。詳細のMISS SLOWは9しか得られず、真値6を他項目から補完せず手入力する必要がある。KiLLKiSSの通常GREATも未読取（画像上3）で手入力が必要。最新の89件回帰・33枚解析・実UI確認は `Verification.md` の2026-10-02記録を参照する。
- 同スコア・同コンボや類似ハッシュは同一プレイの候補にすぎない。知覚ハッシュは同レイアウト・ハミング距離6以下で候補を提示し、自動除外しない。
- 通常／詳細の確認待ちペアは曲名・難易度・スコア・コンボ等で候補化し、明示統合する。既知値の矛盾は拒否し、確認待ち・入力・既存履歴を失わせない。
- SHA一致は登録済み結果と同一バッチ内で除外する。設定画像はプレイの画像指紋として恒久保存しないため、後日の再取込では設定の確認待ちに再登場する。これは現在の仕様。
- 新規プレイは自動登録しない。すべてタイミング確認を経由し、通常／詳細の統合と明示登録を行う。既存プレイへの追加画像の統合では現在の固定値を過去へ流用しない。
- 撮影日時と実プレイ日時を区別する。メタデータがなければ対応形式のファイル名だけを日時候補にし、元名・パス・生メタデータやファイルシステム日時は保存しない。タイムゾーンなしはAsia/Tokyoの仮定を記録する。通常／詳細の最も早い候補を初期選択し、同一画像の日時根拠が競合すれば自動採用しない。既存履歴への追加画像統合では既存日時と設定を保持する。日時未指定なら登録日時を既存の表示順・グラフに使用する。旧履歴へ撮影日を遡って補完しない。

### 統計とタイミング候補

- 各判定率：5判定の総数がすべて既知のプレイだけを対象とし、ノート数で加重する。
- FAST/SLOW比率：PERFECT＋GREATの詳細が揃ったプレイの件数で加重する。プレイごとの比率の単純平均へ変えない。
- FC/AP率：達成状態が既知のプレイ数を分母とする。一覧の達成数は現行マスタの譜面数を分母とする。両者を混同しない。
- レベル別集計は現在のマスタレベルではなく `levelAtPlay`。不明のグループも保持する。標本SDは分母n−1で、1プレイでは不明。
- 個別譜面の偏りは確認済みの全履歴を対象にし、設定が異なる履歴を含むと表示する。調整候補は同一ゲーム・既知譜面・環境ID・全設定に一致する確認済み履歴に限定する。固定端末ポリシーは端末別名・旧履歴の空欄を許容して音声出力と条件メモをまとめ、厳格ポリシーはそれらも一致させる。
- 譜面ごとに`orderDate`降順・UUID文字列昇順の同時刻規則で直近10件を一度選び、全体と`levelAtPlay`別に同じ集合を分ける。異なる3曲以上（同一曲の別譜面は1曲）、P＋G詳細500件以上、曲ごとの詳細加重biasの単純平均が絶対値10%以上、詳細件数で加重した全体biasも同方向、3分の2以上の曲が同方向で1ステップだけ提案する。方向一致率の分母には偏りゼロの曲を含める。
- 十分なデータがあるレベル帯の候補方向が互いに逆、または全体候補と逆なら全体の数値候補を保留する。低データのレベル帯は全体を止めない。プレイ時レベル不明は全体に含め、不明レベル群にはレベル別候補を出さない。全体候補を実際に記録するUIは環境上部の「ゲームで変更した値を記録する…」で、ゲームで設定した確認を必須とする。
- 単位・刻み・範囲・増減方向が不明なら保留。画面の小数桁や54ms表示から仕様・正確な遅延時間・最適値を推定しない。ノーツタイミングと譜面位置を同時に調整しない。2026-10-03の曲横断タイミングの集計・候補・分析ルール版2は回帰テストで確認済み。ゲーム側の改善効果は未検証。

### 保存の原子性

- 現在は `AppState` のJSONをSwiftDataの1行に保存する方式。`schemaVersion = 1`、`StorageSchemaV1`、移行ステージはまだ空。正規化されたSong/Chart別テーブルではない。
- `commit` は保存成功後だけメモリ状態を更新する。失敗時はrollbackし、既存DBを初期化・上書きしない。未対応スキーマや壊れた保存データは起動エラーにする。
- `mergePending` は修正値と統合後の値をすべて検証してから確認待ちを変更する。登録成功前にプレビューを消さない。解析中は確認・統合・登録を拒否する。
- 保存形式の変更が必要になったら、SwiftDataスキーマとJSON payloadの両方の互換性・移行テストを設計する。画像を保存していないので、過去履歴を原画像から再構築できる前提を置かない。

## 次に進める作業候補

新しいユーザー指示が来るまで追加機能を自動で開始しない。以下は再開時の推奨順序で、すでに実施済みのUI検証を最初からやり直す必要はない。

1. AFM実装後の最新テスト・Release生成・署名・対応OS・モデル利用可否フォールバックの検証状況は `Verification.md` を参照する。今回の7画像でOCR・統合・保存・重複除外とAFMの実モデル・署名アプリ操作を確認済み。
2. 楽曲追加の更新依頼時は `Scripts/update_catalog.py` で各サイトを再取得し、既存JSONの固定IDを保持する。照合エラー時は手入力で埋めず原因を確認し、生成・検証後にアプリへ同梱する。
3. 仕様確認済みプリセットを受領したら、現行固定ID `our-notes-results`／`gameId: our-notes` を保ち、版を増やして更新する。単位・刻み・範囲・SLOW改善方向を確認し、旧履歴の版を保持する。十分な同一条件の実プレイが得られたら数値候補を検証する。
4. 自動収集や出典を拡張する場合は `CatalogFormat.md` と既存の回帰テストに従う。定期実行は別途依頼があった場合に設定する。アプリDBへ収集ツールから直接書き込まない。
5. 実サンプル・必要性に合わせて未検証項目を優先する。他タイトル・レイアウト追加・配布対応などは新たな依頼後に着手する。

## 作業環境の補足

- 前のMacの通常アプリDBには、上記3プレイ・6指紋と部分マスタ、現在設定が残っている。端末・音声出力は不明のまま。これはソースや同梱初期データではなく、MBA側に自動で存在するものではない。
- 正規マスターを新規・既存DBへ起動時に自動適用する。単体テスト専用の空マスターが必要な場合だけ `AppModel(loadBundledCatalog: false)` を使う。
- 引き継ぎ時点で `.build` と検証用画像コピー・一時ログ・一時DBは整理済み。`dist`の署名済みアプリは保持。テストを再実行すればビルド中間生成物は再生成される。
- 開発・検証用の不要な一時ファイルは作業後に削除する。原画像、ユーザーの保存履歴、今後必要なファイルは削除しない。
- ユーザーの作業方針：独立した確認作業は品質を検証できる範囲でLunaへ委任し、設計・状態変更・整合性・最終レビューは主担当が確認。小さな作業は委任コストを考慮して直接処理してよい。
- Git公開はユーザーが依頼した場合に行う。通常の既存upstreamへの非force pushはその依頼が承認であり、コミットメッセージは日本語。秘密情報・runtimeデータ・バックアップ・無関係な変更を含めない。現状はGit未初期化なので、設定済みupstreamがある前提でコマンドを実行しない。

## 固定タイミングUIの追加（2026-10-02）

環境の`settings.noteTiming`を固定値、プレイの`environment`をその時の値として利用し、SwiftData／JSONのschemaVersionは1のまま。保存時に変更有無だけ確認し、変更なら固定値と新規プレイを1回の保存で更新する。不明なら今回のスナップショットだけnil。初回の0.10候補も明示保存まで確定しない。一般環境編集はタイミング専用UIへ分離し、古い画面による上書き・刻み外・範囲外を拒否する。
